# Feature F2 — Shared TypeScript Package

**Module:** `packages/shared/`
**Priority:** P0
**Depends on:** F1 (smart contract — for ABI export)
**Paper section:** Notation table (lines 1346–1409).

---

## Purpose

Common types, ABI, and utilities consumed by `coordination-hub`, `dapp-portal`, `management-portal`, and `experiments`. Single source of truth that prevents drift between client and server.

---

## User stories

- **US-SP-1.** As a **frontend developer**, I want to import strongly-typed `ProjectMetadata` and `VerificationOutcome` from one package so that hub, dApp, and management portal can't silently disagree on field names.
- **US-SP-2.** As a **smart contract developer**, I want the ABI to be exported automatically after `forge build` so that frontend doesn't drift from contract.
- **US-SP-3.** As a **test author**, I want a `sha256(sid)` helper that exactly matches the contract's on-chain hashing so that fixture data is consistent.
- **US-SP-4.** As a **reviewer**, I want all paper notation symbols (`phi`, `sid`, `h_i`, `addr_P`, `R`) to map 1:1 to TypeScript names so that I can map code back to the paper.

### ABI export

- `packages/shared/src/abi/ProductRegistry.json` — generated by a script `pnpm shared:build-abi` that reads `contracts/out/ProductRegistry.sol/ProductRegistry.json` (Foundry build output) and writes a stripped-down ABI.
- Re-exported from `packages/shared/src/index.ts` so consumers do `import { ProductRegistryABI } from '@qr-bc/shared'`.

### Hashing helper

```typescript
// hashing.ts
import { sha256 } from '@noble/hashes/sha256';
import { bytesToHex, hexToBytes } from '@noble/hashes/utils';

/** SHA-256 hash of sid bytes — must match the on-chain `sha256()` precompile result. */
export function hashSid(sid: Uint8Array | string): `0x${string}` {
  const bytes = typeof sid === 'string' ? hexToBytes(sid.replace(/^0x/, '')) : sid;
  return `0x${bytesToHex(sha256(bytes))}`;
}

/** Generate a random sid via Web Crypto / Node Crypto. */
```

## Edge cases

| #       | Scenario                                      | Expected behavior                                                   |
| ------- | --------------------------------------------- | ------------------------------------------------------------------- |
| EC-SP-1 | `hashSid('')` (empty string)                  | Returns `0xe3b0c44...` (well-known SHA-256 of empty). Not an error. |
| EC-SP-2 | `hashSid` with non-hex string                 | Throws `InvalidHexError`.                                           |
| EC-SP-3 | `generateSid(0)`                              | Throws `InvalidByteLengthError`; minimum 16 bytes.                  |
| EC-SP-4 | ABI build script run before contract compiled | Script exits 1 with clear error: "Run `forge build` first".         |
| EC-SP-5 | Date fields serialized to JSON                | Use ISO-8601 strings; deserialize in API boundary layer.            |

## Non-goals

- No business logic (pure types + helpers).
- No framework-specific imports (no React, no NestJS).

> **Note (amended 2026-05-05):** an earlier draft of this doc listed
> "no runtime validation library (Zod) here" as a non-goal. That was
> reversed during Phase 2 implementation (T-011) — see Phase 2 review
> §2.3 and §I-1 for the rationale. The hub, dApp, and management portal
> all need the same validation logic on `ProjectMetadata` /
> `CultivationActivity` / `Certification`; keeping a single set of
> schemas in `@qr-bc/shared` eliminates a 3× duplication risk. The
> schemas are gated behind a subpath import (`@qr-bc/shared/schemas`)
> so type-only consumers that don't want the `zod` runtime dep can
> keep importing only from the root entry point.
